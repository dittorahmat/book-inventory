# Aturan Testing, CI & Otomasi

Dokumen ini memuat aturan kanonik dan mandat anti-kambuh untuk pengujian unit/E2E, isolasi test, otomasi browser Playwright, performa gate CLI, dan disiplin tooling.

---

## Mandat Anti-Kambuh

### §0.13. Disiplin PowerShell & Shell Tools
1. Saat menjalankan perintah CLI yang menulis teks multibaris / markdown bertanda backtick (misal `gh pr create --body`), hindari interpolasi string inline langsung di PowerShell pwsh karena karakter backtick ` dapat memicu error escape sequence; gunakan argumen file (`--body-file <file>`) atau single-quoted here-string (`@' ... '@`). Untuk pembuatan Pull Request, tulis ringkasan perubahan ke file temporer terlebih dahulu melalui tool `write_file` (misal `.pr-body.txt`) lalu jalankan `gh pr create ... --body-file .pr-body.txt` dan hapus berkas tersebut setelah PR dibuat.
2. Pembuatan dan pelepasan git worktree dilarang merakit string pwsh mentah (`git worktree add ...`), wajib menggunakan runner otomatis `bun run worktree:add` dan `bun run worktree:remove` (§0.51.4 & §0.51.6).
3. **Disiplin Pencarian Teks PowerShell**: Untuk pencarian string literal yang mengandung tanda kutip di shell `pwsh`, dilarang merakit escaping regex kompleks (`rg "type=[\"']number[\"']"`) yang rentan gagal parse di PowerShell; wajib gunakan opsi fixed string `rg -F 'type="number"'` atau string bertanda kutip tunggal literal guna menghemat token dan tool turns.

### §0.17. Disiplin Artefak Bersih & Anti-Blob Liar
Dilarang melakukan commit atas file biner liar atau dokumen presentasi/ekspor PDF/DOCX (`*.pdf`, `*.docx`, dsb.) ke dalam tree git; dokumentasi spesifikasi dan skenario sistem wajib berformat teks markdown murni (`.md`). Ditegakkan mekanis oleh `check:clean-artifacts`.

### §0.18. Integritas Test E2E & Validasi Alur Mutasi Aktif
Integration test E2E skenario bisnis dilarang hanya membaca data pasif (`GET` assertions belaka); setiap skenario operasional (seperti PO pengadaan, transfer shipment kirim-terima, tukar seragam, penolakan bukti bayar, dan pembatalan pesanan) wajib menguji mutasi alur (`POST`/`DELETE`/`PATCH`) hingga status akhir dokumen tervalidasi.

### §0.23. Disiplin Kompilasi Inkremental & Timeout Pre-Commit
`tsconfig.json` wajib mengaktifkan `"incremental": true` dengan `tsBuildInfoFile` terabaikan git (`tsconfig.tsbuildinfo`). Pada Windows pwsh, tipe-checking dan pre-commit hook harus memanfaatkan cache inkremental agar tidak melampaui ambang batas timeout eksekusi tools CLI.

### §0.24. Disiplin Regression Test Delegasi Router-ke-Seam
Setiap ekstraksi logika bisnis dari router Hono ke modul domain/seam (`services/*`) wajib mempertahankan atau menambahkan test di level route (`*.test.ts`) yang memverifikasi pemetaan status HTTP dan payload respons secara eksplisit (termasuk kasus error 400/404/409 dan delegasi parameter alias).

### §0.25. Disiplin Browser Automation & Otomasi E2E
Script otomasi browser (Playwright dsb.) dilarang hanya melakukan inspeksi pasif (sekadar cek tombol atau navigasi tab belaka); setiap skenario wajib mengeksekusi mutasi aktif/aksi form (isi input, klik submit, unggah dokumen), menyimpan bukti tangkapan layar (screenshot visual) pada checkpoint hasil, dan menghindari sleep arbitrer (`waitForTimeout` membabi-buta) dengan mengutamakan asersi web eksplisit (`waitForLoadState`, `toBeVisible`, atau penantian elemen spesifik).

### §0.32. Disiplin Asinkron Tooling & Anti Polling/Looping
Hindari perulangan aktif / polling status berulang-ulang pada background tasks (`manage_task status` / `manage_task kill`) atau command shell. Sistem otomatis memberikan notifikasi saat background task selesai. Bila menjalankan perintah shell yang diharapkan terminasi cepat (termasuk `bun run check:fast` atau `git commit`), gunakan nilai `WaitMsBeforeAsync: 10000` (10 detik) agar selesai secara sinkron dalam satu turn tanpa memicu siklus polling status background task yang membuang kuota pesan dan token context. Untuk pencarian teks di Windows pwsh, gunakan `git grep` atau `rg` native langsung, dilarang membungkus dengan syntax `rtk proxy` yang tidak kompatibel dengan flag sub-tools.

### §0.33. Pencegahan File-Size Overflow Saat Penambahan Route Actions
Route file (`src/server/routes/*.ts`) yang telah mendekati batas 400 baris (>=350 baris) dilarang langsung ditambahi logika endpoint baru; pecah endpoint ke sub-router fungsional (misal `*-actions.ts` atau delegasi penuh ke `services/`) sebelum mendaftarkan route baru, guna mencegah refactoring darurat di akhir tiket. Ditegakkan mekanis dengan peringatan dini otomatis oleh gate `check:file-size`.

### §0.36. Disiplin Navigasi & Persistensi Spesifikasi Desain
Spesifikasi arsitektur atau rencana implementasi yang dihasilkan dari skill perancangan (`/improve-codebase-architecture`, `/plan`, dsb.) dilarang hanya ditinggalkan pada file temp sistem operasi (`%TEMP%` / `/tmp`) yang rentan terhapus atau sulit dijangkau sub-agent review; sertakan tautan / ringkasan spesifikasi di commit message awal atau simpan artefak rencana di `.scratch/` / `openspec/changes/` agar sub-agent peninjau spesifikasi (`/code-review` spec axis) memiliki akses langsung ke dokumen acuan kebenaran (*single source of truth*).

### §0.37. Ekonomi Eksekusi Test & Gate pada Pengembangan Aktif
Selama siklus perubahan aktif per tiket, prioritaskan `bun test <file>` dan `bun run check:fast` (yang mengeksekusi gate inkremental secara instan); hindari menjalankan `bun test` penuh atau `check:all` di setiap iterasi kecil karena suite 550+ test membutuhkan waktu ~60 detik dan berpotensi menghabiskan batas asinkron shell. Jalankan `check:all` penuh hanya sekali pada tahap verifikasi akhir sebelum commit atau pembukaan Pull Request.

### §0.40. Integritas Penegakan Asersi E2E & Isolasi Actor Test
Pengujian mutasi aktif skenario bisnis (E2E) dilarang membungkus asersi mutasi utama dalam pengkondisian pasif (`if (collection.length > 0)`) yang berpotensi dilewati diam-diam (*silent skip*); susun precondition data (misal binding paket fisik atau kuantitas stok awal) secara deterministik dan lakukan asersi mutasi saldo/kolom secara langsung. Selain itu, pemanggilan `mockActor` di suite test wajib mendampingkan `restoreActor()` di hook siklus hidup `afterEach()` atau blok `finally` guna mencegah kebocoran sesi otentikasi antar berkas test. Ditegakkan mekanis oleh gate `check:test-isolation`.

### §0.41. Disiplin Skema Input Ketat & Anti-Silent Drop (Zod Strict)
Endpoint intake publik yang menerima dokumen/bukti (seperti komplain retur atau pembatalan pengunduran diri) wajib menggunakan `.strict()` pada schema validator Zod agar kesalahan ketik nama kunci payload (typo key) ditolak secara eksplisit dengan status 400 Bad Request, bukan dilewati diam-diam menjadi `undefined`. Selain itu, loop `check:fast` wajib menjalankan linting inkremental pada berkas yang diubah guna mencegah alokasi memori heap berlebih (out-of-memory).

### §0.42. Disiplin Otomasi Browser & Autentikasi Reset Demo
Skrip otomasi browser Playwright (`scripts/demo-scenarios/*`) dilarang hanya mengisi input tanpa men-submit form atau membiarkan mutasi aktif berhenti di level screenshot belaka; setiap alur formulir (murid baru, retur komplain, pembatalan pengunduran diri, serah terima, dan approval retur) wajib mengeksekusi klik submit/konfirmasi. Pemanggilan endpoint reset database demo (`POST /api/demo/seed`) wajib menyertakan otentikasi sesi Central Admin sah via browser context (`page.request.post`), dilarang menggunakan fetch mentah tanpa header yang berujung pada penolakan 401/403.

### §0.43. Verifikasi Lingkungan Bersih & Zero-Error-Banner pada Otomasi Demo
Eksekusi otomasi demo (`demo:automate`) wajib dijalankan di atas server backend + klien frontend aktif yang terhubung (port 5173 dengan proxy API 3000), dengan pre-flight check sinkronisasi database SQLite lokal tersinkronisasi penuh (`bun run db:push:bun --all`) tanpa toleransi silent-catch. Seluruh tangkapan layar hasil di `test-results/demo-screenshots/` wajib terbebas dari banner/alert kegagalan server ("Terjadi kendala pada server" atau "Dashboard gagal dimuat"). Runner wajib memasang response error interceptor (`attachErrorFailFast`) di tingkat `BrowserContext` (agar mencakup seluruh tab, popup, dan halaman baru) dengan objek error terstruktur (`InterceptedError`) yang memicu error fail-fast langsung (`immediateThrow: true`) seketika terdeteksi HTTP >= 500 atau unhandled page crash, dilarang menunda atau men-swallow kegagalan server. Pada modal serah-terima buku (`OrderHandoverModal.tsx`), tombol konfirmasi disabled hingga kode pengambilan diisi cocok; skrip otomasi wajib menginput kode cross-check secara deterministik (`waitFor({ state: "visible" })`) dan menunggu tombol aktif via `waitForFunction` tanpa memakai `waitForTimeout` arbitrer atau guard kondisional pasif yang berisiko silent-skip (§0.25, §0.40).

### §0.49. Hardening Keamanan Otentikasi, Asal Muasal (Origins), dan Intake Publik
1. **Anti-Wildcard Trusted Origins**: `trustedOrigins` pada konfigurasi auth (Better-Auth) wajib berupa daftar literal domain eksplisit (misal `http://localhost:5173`, domain workers/pages produksi), dilarang menggunakan wildcard regex (`/^https:\/\/.*\.workers\.dev$/`) yang mempercayai domain pihak ketiga sembarangan.
2. **Penutupan Total Self-Registration Publik**: pencegahan registrasi mandiri publik di route handler auth (`/api/auth/sign-up/*`) wajib mencakup seluruh metode HTTP (`app.all(...)` atau intersepsi fail-closed) dengan status 403 Forbidden.
3. **Disiplin Batas Karakter & Ukuran Upload Base64 (Anti-Memory DoS Worker)**: seluruh schema input publik yang menerima payload base64 dokumen/bukti (buku, seragam, pembatalan, dan retur) wajib memakai validator kanonik `base64UploadSchema` dengan batas eksplisit `MAX_BASE64_UPLOAD_CHARS` (maksimal 7.000.000 karakter / ~5MB decoded binary) guna melindungi alokasi memori heap Cloudflare Worker (128MB). Konstanta batas panjang string karakter wajib dinamai secara presisi (`_CHARS`/`_STRING_LEN`), bukan `_BYTES`.
4. **Fail-Closed Secret Produksi**: helper auth wajib memverifikasi ketersediaan secret server (`BETTER_AUTH_SECRET`) pada mode produksi (`NODE_ENV === "production"`) dan melempar error fail-fast tanpa fallback ke nilai rahasia development statis.

### §0.51. Disiplin Eksekusi Test Terfokus & Ekosistem Unit Test Komponen
1. **Target File Eksplisit pada Test Runner**: eksekusi test pada siklus iterasi aktif wajib selalu menargetkan berkas secara eksplisit (`bun test <path/file.test.ts>`), dilarang menjalankan `bun test -t <pattern>` tanpa argumen path file karena akan memicu seluruh test suite (550+ test) dan berisiko timeout asinkron shell.
2. **Shim DOM Wajib pada Test Komponen (`*.test.tsx`) & Isolasi Helper Logika**: setiap pengujian komponen React yang merender DOM (`render(...)`) wajib mengimpor shim DOM kanonik (`import "../../test-dom"`) pada baris pertama dan melakukan dynamic import `@testing-library/react` guna mencegah runtime error `document is not defined` di lingkungan Bun. Logika kalkulasi, transformasi, dan filter domain UI wajib diekstrak ke helper murni terisolasi (`*-helpers.ts`) yang diuji terpisah via unit test tanpa DOM (`*-helpers.test.ts`) untuk mencegah crash alokasi memori heap Happy-DOM pada Bun Windows.
3. **Disiplin Deklarasi Path Tooling**: pemanggilan tool manipulasi berkas (`read_file`, `write_file`, dsb.) wajib selalu menggunakan path absolut lengkap (berbasis root project `D:\development\book-inventory\...`), dilarang mengoper path relatif yang memicu error permission.
4. **Penyiapan Worktree & Junction Dependencies (`bun run worktree:add`)**: pembuatan git worktree baru wajib menggunakan script otomatisasi `bun run worktree:add <branch> [target-dir]` (`scripts/worktree-setup.ts`). Script ini otomatis mengeksekusi `git worktree add` sekaligus membuat junction/symlink `node_modules` dari repositori utama, sehingga runner test dan compiler TypeScript langsung berfungsi tanpa error import modul (`Cannot find package ...`). Setiap implementasi tiket/fitur via skill `implement-spec` wajib memilih salah satu direktori kosong di antara `book1`, `book2`, atau `book3`; dilarang melakukan pekerjaan langsung di root `book-inventory`.
5. **Pembersihan Berkas Usang Saat Ekstraksi Komponen**: saat mengekstrak komponen atau memindahkan tanggung jawab ke berkas baru (misal memecah sub-komponen UI), berkas lama yang tidak lagi memiliki perujuk wajib segera dihapus dari disk sebelum tahap staging/commit agar pre-commit gate `check:dead` tidak mendeteksi export yatim piatu.
6. **Pelepasan & Pembersihan Worktree (`bun run worktree:remove`)**: setelah branch di-merge ke `main`, pelepasan worktree dan penghapusan branch lokal terkait wajib menggunakan perintah kanonik `bun run worktree:remove <branch-atau-dir>` (`scripts/worktree-cleanup.ts`) untuk menghindari kegagalan pelepasan branch aktif atau folder worktree tertinggal. Jika merge PR dilakukan lewat GitHub CLI (`gh pr merge`), hindari penggunaan flag `--delete-branch` saat git worktree untuk branch tersebut masih aktif terpasang di disk lokal; lepaskan worktree via `bun run worktree:remove` terlebih dahulu agar tidak memicu error git ref locking.
7. **Peta Lokasi Test Suite & Isolasi Mutasi Demo**: berkas test terbagi menjadi tiga ranah utama:
   - Pengujian domain, unit, layanan server, komponen UI, route, dan seed demo bersifat co-located di bawah `src/**/*.test.ts(x)` (misal `src/server/generate-sd-student-orders.test.ts` atau `src/server/seed-demo/demo-uniform.test.ts`). Jangan mencari test server di bawah `test/server/` karena seluruh unit test server tinggal bersama implementasinya di `src/server/`. Setiap modul API klien antarmuka (`*-api.ts`) yang membungkus query builder / pemanggilan endpoint wajib memiliki unit test pendamping (`*-api.test.ts`) guna memverifikasi kelengkapan propagasi parameter query string.
   - Pengujian skrip otomatisasi di bawah `scripts/` wajib co-located di `scripts/*.test.ts`, dilarang diletakkan di dalam `src/` guna mencegah pelanggaran batas import (`check:imports`).
   - Pengujian integritas lingkungan, arsitektur, dan infrastruktur global berada di `test/**/*.test.ts`.
   Test yang mengeksekusi demo seed wajib menjaga isolasi mutasi data agar tidak merusak ekspektasi test paralel/konkuren di lingkungan runner CI.
8. **Disiplin Isolasi Fixture Test, Pembersihan Siklus Hidup & Larangan Unqualified Delete**: seluruh unit/integration test yang melakukan insert state entitas induk atau saldo stok (`schools`, `books`, `students`, `book_stocks`, dsb.) wajib membersihkan baris yang dibuat di hook `afterEach()` atau blok `finally`, atau menggunakan ID dinamis acak (`test/fixtures.ts`) guna mencegah benturan constraint (`duplicate key` / `foreign key`) saat runner Bun mengeksekusi file test secara konkuren/paralel. Dilarang keras melakukan blanket delete (`db.delete(<table>)` tanpa klausa `.where(...)`) pada tabel master (`bookPackages`, `books`, `schools`, `students`, `uniformVariants`, dsb.) karena akan menghapus seluruh data baseline katalog yang dibutuhkan oleh file test lain dalam satu proses test runner. Jika pengujian memerlukan simulasi katalog kosong, gunakan teknik mocking/spying pada query session Drizzle alih-alih menghapus data fisik. Pengujian filter ruang kelas / rombel server-side wajib menyertakan fixture multi-jenjang (minimal 2 jenjang berbeda dengan nama ruang seksi serupa, misal `1 INTER 1` dan `2 INTER 1`) guna memverifikasi bahwa query partisi tidak menimpa data antar jenjang kelas. Ditegakkan mekanis oleh `check:test-isolation`.
9. **Disiplin Subagent Review & Fallback Inline di Windows Sandbox**: pemanggilan subagent untuk review (`research`) pada lingkungan Windows jika mengalami kendala socket network (`connectex`) wajib segera fallback ke review inline langsung pada agent utama dalam 1 turn tanpa membuang token dan waktu perulangan.

### §0.58. Disiplin Portabilitas Skrip & Parity Test Seed Data
1. **Dilarang Hardcoded Host Path & Referensi Lintas-Worktree**: Seluruh skrip di `scripts/**` dan modul parser dilarang keras memuat path lokal host absolut (`D:/...`, `C:/...`) maupun referensi path naik lintas worktree (`../book-inventory/...`). Input berkas wajib menerima parameter CLI (`process.argv[2]`) atau environment variable dengan default path relatif repositori (`./data/...`) serta penanganan error informatif jika file tidak ditemukan. Ditegakkan mekanis oleh `check:no-hardcoded-paths`.
2. **Automated Parity Test untuk Data Seed Kompleks**: Seeder atau import yang merakit relasi agregat (seperti harga paket bundling = subtotal BOM buku) wajib disertai automated parity unit test di CI guna menjamin tidak adanya selisih harga atau item yang terlewat.
3. **Kanonikalisasi Seeder Data & Larangan Raw Mutasi di Scripts**: Skrip pengisian data di `scripts/` dilarang merakit raw `INSERT INTO` ke tabel inti (seperti `book_stocks`, `uniform_stock`, `payment_receipts`, atau `payment_allocations`). Seluruh pembaruan saldo atau mutasi wajib memanggil runner/seam domain kanonik yang mematuhi arsitektur single-writer (`moveInventoryStock`, `seedInitialBookStock`, `payment-ledger`). Ditegakkan mekanis oleh `check:single-writer`.
4. **Isolasi Database Uji Skrip di CI**: Test pengujian skrip (seperti generator SQL sinkronisasi) dilarang berasumsi adanya file database lokal riil (`./data/inventory.db`) di runner CI. Test wajib membuat database SQLite in-memory / temporary mandiri yang ditutup (`db.close()`) dengan rapi agar tidak mengunci file di Windows dan tidak melakukan silent skip (`expect(true).toBe(true)`).

### §0.60. Disiplin Dekomposisi Proaktif Modal UI & Pemisahan Baris Transaksi
1. **Dekomposisi Proaktif Komponen UI (>300 Baris)**: komponen modal atau form UI yang telah memiliki >300 baris sebelum dimodifikasi wajib didekomposisi terlebih dahulu ke sub-komponen terpisah (misal memisahkan form header/fields dan list/row item transaksi ke berkas terpisah seperti `PoHeaderFields.tsx` dan `PoItemRow.tsx`) sebelum penambahan state atau fitur baru, guna mencegah terjadinya overflow batas arsitektur 400 baris secara reaktif.
2. **Efisiensi Pemeriksaan Drift Remote D1**: pemeriksaan remote D1 (`check:d1-drift`) pada gate inkremental `check:changed` dibatasi hanya berjalan jika secara eksplisit diaktifkan via environment variable (`CHECK_D1_REMOTE=1`), guna menghindari blocking shell timeout ~10 detik dan false warning saat pengembangan lokal offline.
3. **Penyediaan Snapshot Mock Seeder Pengadaan**: pengujian dan pengetesan lokal alur PO pengadaan dapat memuat relasi katalog-vendor contoh via fixture `src/server/seed-demo/procurement.ts` tanpa harus bergantung pada data produksi remote.
4. **Proactive File-Size Scaffolding & DOM Shim Hygiene**: Pada saat membuat atau merefaktor komponen modal UI interaktif, agen wajib memecah section picker dan item card sejak awal bila diperkirakan mendekati 300 baris. Seluruh unit test React DOM di lingkungan Bun Windows wajib mengimpor `../../test-dom` di baris pertama dan menggunakan dynamic import `@testing-library/react` guna mencegah ReferenceError document is not defined.
5. **Definisi Ruang Lingkup Tiket & Eksklusi Notifikasi Eksternal**: saat merancang tiket baru (`/to-tickets`), setiap tiket yang bersinggungan dengan kanal notifikasi eksternal (WhatsApp, Email) wajib memiliki seksi eksplisit batas lingkup (*Out of Scope*) guna mencegah implementasi auto-trigger yang tidak diinginkan pengguna.
6. **Ekonomi Waktu Eksekusi Test Komponen DOM & Background Task**: suite pengujian komponen DOM (`*.test.tsx`) dan `check:all` yang memicu bundle Vite membutuhkan waktu ~15-25s di Windows pwsh; saat TDD filter skenario secara spesifik per file dan per nama test (`-t "..."`) agar tetap selesai <2s, dan biarkan notifikasi sistem menangani background task tanpa polling status berulang-ulang (§0.32).

### §0.77. Hard-Gate CI/CD & Disiplin Larangan Merge Sebelum Checks Pass
1. **Larangan Keras Merge Tanpa Checks Hijau**: Agen dilarang keras mengeksekusi merge PR (`gh pr merge`) maupun menyarankan merge kepada pengguna sebelum status checks GitHub Actions (`gh pr checks <PR>`) secara nyata bernilai `pass` (hijau). Dilarang memakai flag bypass `--auto` yang berisiko mengeksekusi merge saat checks sedang berjalan atau berujung gagal.
2. **Isolasi File Runner Bun Test dari Framework Eksternal**: `bun test` secara default mengeksekusi pola file `*.test.ts` dan `*.spec.ts`. File test framework eksternal (seperti Playwright browser spec) dilarang menggunakan ekstensi yang memicu pemindaian `bun test` tanpa dependensi runtime terpasang, atau wajib dipisahkan runner-nya secara eksplisit (`scripts/demo-scenarios/*`).
3. **Branch Protection & Require Checks Pass**: Branch `main` wajib dilindungi oleh konfigurasi Branch Protection di GitHub Settings dengan opsi *Require status checks to pass before merging* (memilih context check `gates`), memastikan repositori menolak mutasi langsung jika gate CI gagal.

### §0.78. Disiplin Deep Modules, Anti-Shallow Wrappers & Gate Test Otomatis
1. **Larangan Middle Man / Shallow Wrapper**: Dilarang membuat modul wrapper tipis yang hanya meneruskan argumen tanpa abstraksi nilai tambah nyata (seperti fungsi facade yang hanya memanggil fungsi lain satu baris). Setiap modul atau fungsi baru wajib menerapkan prinsip *Deep Module* (antarmuka sederhana menyembunyikan kompleksitas besar), bukan sekadar perantara (middle man) yang memicu duplikasi atau YAGNI.
2. **Koneksi Wajib ke Pemanggil Nyata (Wired Up)**: Setiap pembuatan modul domain atau seam baru wajib langsung dihubungkan (*wired up*) ke route handler atau pemanggil nyata dalam PR yang sama. Dilarang menyisakan modul baru berstatus mengambang (unintegrated/dead-code) yang hanya diuji oleh unit test-nya sendiri tanpa integrasi ke alur transaksi sistem riil.
3. **Eksekusi Otomatis Berkas Test yang Berubah pada Gate Pre-Commit (`check:fast`)**: Setiap berkas test unit/integrasi (`*.test.ts(x)`) yang mengalami perubahan wajib otomatis dieksekusi oleh runner `check-changed.ts` (`bun test <changed_test_files>`), menjamin kegagalan test atau cacat data/fixture terdeteksi seketika sebelum commit mendarat atau terkirim ke CI.

### §0.87. Disiplin Eksekusi Worktree & Type-Check Pre-Test
1. **Runner Eksekusi Worktree Kanonik (`bun run wt`)**:
   - Pemanggilan test atau skrip di subdirektori worktree (`book1`, `book2`, dsb.) dilarang mengandalkan argumen `Cwd` pada `run_command` (tidak didukung tool schema) atau menjalankan `bun test` langsung dari root repositori utama (yang membaca berkas sebelum diedit).
   - Gunakan runner kanonik `bun run wt <worktree_dir> <cmd...>` (e.g. `bun run wt book1 test src/lib/book-import-parser.test.ts`), atau navigasikan shell eksplisit `cd <worktree_dir>; bun <cmd>`.
2. **Type-Check Mendahului Runtime Test & Guard Transformer**:
   - Saat menambahkan atau memodifikasi Zod validator schema yang memiliki transformator (`.transform(...)`), agen wajib menjalankan `bun run type-check` sebelum mengeksekusi test guna memastikan seluruh dependensi fungsi pembantu (seperti `normalizeCanonicalCurriculum`) telah diimpor dengan benar dan bebas dari `ReferenceError` di runtime.
3. **Penjagaan Helper Kanonik Kurikulum (`check:canonical-helpers`)**:
   - Helper kanonik kurikulum `isCambridgeInternationalTitle`, `inferCurriculumFromText`, dan `sqlNormalizeCurriculum` (`src/lib/curriculum.ts`) wajib digunakan sebagai sumber kebenaran tunggal (*single source of truth*) untuk identifikasi program kurikulum Al-Wildan, dilarang menduplikasi regex substring ad-hoc maupun raw SQL normalisasi di parser, komponen view, atau query database. Ditegakkan mekanis oleh `check:canonical-helpers`.
4. **Isolasi Entitas Uji & Pencegahan Test Leak Antar-File**:
   - Setiap test yang menambahkan data entitas transaksional atau registrasi murid publik (`students`, `orders`, `purchase_orders`) wajib membersihkan seluruh ID baris yang dihasilkan pada blok `finally` atau hook `afterEach` (§0.51.8). Dilarang meninggalkan entitas yatim (*orphan records*) yang dapat terakumulasi pada runner proses tunggal `bun test` di CI dan mencemari kalkulasi demand/agregasi file tes lain.
5. **Disiplin Deklarasi Tipe Mock Variabel Uji & Wildcard Pencarian Shell**:
   - Variabel penampung hasil mock/spying pada closure test wajib dideklarasikan dengan tipe eksplisit (`let bumpedKey: string | null = null`) dan asersi `expect(bumpedKey as string | null).toBe(...)` guna mencegah type-checker `tsc` menolak pemanggilan akibat inferensi tipe literal `null` yang terlalu sempit.
   - Pemanggilan pencarian teks `rg` di shell Windows pwsh dilarang meneruskan karakter wildcard glob tanpa tanda kutip (misal `rg pattern src/seed*.ts` memicu os error 123); wajib gunakan argumen bertanda kutip tunggal literal atau flag `-g 'src/seed*.ts'`.
